CLI AI エージェント間 IPC インフラ

agmsg-go はどう通信するか

共有された 1 個の SQLite ファイルを「郵便ポスト」にして、Claude Code / Codex / Gemini などの エージェントが直接読み書きで連絡し合う。中央プロセス(broker / daemon)もネットワークも持たない。 設計のアイデアは bash 製 fujibee/agmsg に由来。

“No daemon, no network, no complexity”

全員が同じ単一バイナリ agmsg のサブコマンドを叩くだけ。 agmsg 自身は常駐 broker を持たない。逐次書き込み + 同時読み取りを成立させる土台が WAL モード(→ 07)。
02

宛先 = (name, team)

project path / type はメタデータ

join で参加

agmsg join <team> でチームに登録。teams/<team>/config.json に registration が積まれる。通信の前提。

名前 + チームで識別

「名前とチームの組」で同一性を判定。同じ (name, team) なら別 project から join しても同一アイデンティティ。送受信はこの組で絞られ、無関係な第三者には届かない。

1 人で複数役も

actas / drop で 1 セッションが reviewer・implementer など複数の役割を演じ分けられる。

03

メッセージ 1 通の流れ

送信 = INSERT / 受信 = 2 経路

送信 agmsg send

1 行 INSERT するだけ。placeholder バインド(?) で渡すため、本文に ' ; 改行 が含まれても SQL インジェクション・構文破壊が起きない。文字列連結で SQL を組み立てない。

受信は 2 つ(性質が違う → 05)

inbox(消費): 未読 read_at IS NULL を取得し既読化。
watch(閲覧): id > watermark を既読化せず stream。

-- messages テーブル CREATE TABLE messages ( id INTEGER PRIMARY KEY AUTOINCREMENT, -- 単調増加 → watermark に使う team TEXT, from_agent TEXT, to_agent TEXT, body TEXT, created_at TEXT, read_at TEXT -- NULL = 未読 );
04

受信検知 — fsnotify(主) + ポーリング保険

internal/watch

主: fsnotify(DB ディレクトリ監視)

  • OS のファイル変更通知で実質即時にトリガ
  • イベントのバーストは 50ms debounce で 1 回に畳む
  • 監視対象は DB ディレクトリ全体(WAL の罠 → 07)

保険: 30 秒ポーリング

  • 実体は time.Ticker 1 個
  • fsnotify が取りこぼしても最大 30 秒で必ず追いつく
  • 主が即時なので案 A の 5 秒より長くしアイドルコスト減
// 2 つのトリガ経路が「同じ取得処理 OnTrigger」を叩く (watch.go) for { select { case <-ticker.C: // ★ ポーリング保険 (30s) cfg.OnTrigger(ctx) case <-events: // fsnotify(主) → debounce を張る if debounce == nil { debounce = time.After(50*ms) } case <-debounce: // 即時取得 cfg.OnTrigger(ctx) } } // OnTrigger = "id > watermark の SELECT" 一本。べき等なので二重発火しても無害。 // fsnotify が死ぬと events を nil 化 → select が選ばなくなり ticker だけで回る(fallback)。
狙いは遅延短縮ではなく「アイドル効率」。 何も来ない間はプロセスを fork せず静かに待つ。 受信の数秒〜数十秒の遅延は LLM の推論時間に埋もれて体感差にならない、という割り切り。
05

watch ≠ inbox — 閲覧と消費は独立

なぜ分けるのか
watch(閲覧 / 通知)inbox(消費 / 処理台帳)
実体store.Sincestore.TakeUnread
SQLSELECT WHERE id > ?UPDATE SET read_at WHERE read_at IS NULL RETURNING
未読の判定軸watermark(プロセスメモリ・揮発)read_at(DB 永続)
副作用なし(read-only)read_at を埋める = claim
比喩tail -f で眺める受信トレイから開封して処理
2 系統は完全に無干渉。 watch で眺めても read_at は NULL のまま → 後から inbox を叩けば同じ 1 件がまだ「未読」として取れる。「眺めた」≠「処理した」。

① both の二重安全網

watch(揮発 watermark)はプロセス死・再起動で取りこぼしうる。永続 read_at が残るから check-inbox が確実に回収できる。

② watch を冪等に再起動

/clear や --resume で再起動するたび MAX(id) から「今から先」を見るだけ。永続状態を汚さない。

③ mechanism, not policy

「読んだら消すか」は利用側の選択。binary は閲覧と消費の 2 プリミティブを提供し、組み合わせは委ねる。

06

配信モードと「No daemon」の正体

どう気づかせ、何を常駐させないか

4 つの配信モード

monitorSessionStart → watch が常駐 stream(即時)
turnStop フック → ターン間に check-inbox
bothmonitor 主 + turn 保険(取りこぼし防止)
off自動配信なし(手動 inbox)

watch は常駐する。だが daemon ではない

ポーリングする以上「走り続けるプロセス」= agmsg watch は実在し常駐する。常駐ゼロではない。

daemon でないのは、watch が独立自走せずホストのセッション寿命に自分の寿命を預けるから。親が消えれば self-terminate する。

✗ 却下: 独立 broker daemon(案 C)

  • 誰が起動・再起動・kill する?
  • 複数バージョンが同時に走ったら?
  • = 自分で管理する常駐プロセスのライフサイクル地獄

✓ 採用: watch が寿命をホストに預ける

  • 起動はホストの SessionStart フック
  • 親が死ねば watch も死ぬ(孤児化しない)
  • = 管理地獄をホスト側に肩代わりさせて回避
「No daemon」は常駐ゼロの意味ではない。 否定しているのは「自分で管理する独立常駐 broker」。 watch の常駐管理(二重起動防止・孤児回収・世代管理)を型とテストで安全にした点が本質。
07

WAL モード Write-Ahead Logging

同時読み書きを成立させる土台

✗ 既定: rollback journal

  • 本体ファイルを直接上書き(元の内容を journal に退避)
  • 書き込み中は読めない / 読む間は書けない
  • 書き手と読み手が排他 → 多人数で待たされる

✓ WAL モード(agmsg 採用)

  • 本体は触らず変更を -wal に追記
  • 読み取りは「本体 + -wal」を合成して最新を見る
  • 複数リーダ + 1 ライタが同時に動ける

3 つのファイル

messages.db(本体) / -wal(追記先) / -shm(索引・共有メモリ)。

checkpoint

溜まった -wal を本体へ反映し空に戻す(truncate / 再作成)お掃除。

監視の罠

書き込みは -wal に乗るので 本体だけ監視すると発火しない。だから DB ディレクトリ全体を監視する(→ 04)。

08

最大の設計判断 — mechanism, not policy

何を作り込まないか

binary が持つ＝ mechanism(不可侵のコア)

send宛先へ INSERT
inbox未読 SELECT + 既読化(消費)
watchid > watermark を stream(閲覧)
join / whoami宛先解決・自己同定

binary が持たない＝ policy(利用側 / skills 層)

「誰にどう振り分けるか」「レビュー→修正をどう回すか」は作り込まない。代表的な使い方だけ 分離・opt-in な skills 層として同梱(binary を IPC 経由で呼ぶ消費者)。

dispatch

別リポで agent を worktree+tmux 起動 → join で team に auto-join。

review-loop

逆 agent に反復レビューさせ収束。verdict 通知を send/inbox に載せる。
